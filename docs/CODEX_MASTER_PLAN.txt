Recommended pragmatic stack

   •       Backend API: Python FastAPI, typed Pydantic contracts and an OpenAPI specification. Keep domain/engineering

   •       Work queue: Redis-backed RQ/Celery (or managed equivalent) for PDF rendering, extraction, catalog imports and

4. Multi-sheet document parsing and materials inventory
Stage 1: Register all pages to the end; preserve page rotation, bounds, source SHA-256, original bytes, printed sheet number and
title block. Handle mixed drawing line IDs in one uploaded PDF and repeated line IDs across files. Detect and distinguish SHT 2
OF 2 from physical page 2.
Stage 2: Extract CAD vector/text where available; some drawing lettering consists of paths and may have little searchable text.
Raster/scanned drawings may yield proposals via OCR/vision but never exact physical stations merely from image recognition.
Retain source bbox/page/recognition confidence for every extracted statement. Template-specific extraction adapters are allowed
but must degrade safely to manual verification.

Stage 3: Parse the materials list with per-sheet inventory {sheet_id, item_no, description_raw, quantity, size,
class, rating, standard, component_type, source_evidence}. Distinguish fabrication vs erection lists and don't
assume item numbers are globally unique. Source quantity is authoritative for audit, not proof that an exact physical location exists.

Stage 4: Match each list item to drawing callouts and observed component instances. Flag MISSING_INSTANCE,
EXCESS_INSTANCE, DUPLICATE_INSTANCE, AMBIGUOUS_MATCH, UNREADABLE_LABEL,
SIZE_MISMATCH or ITEM_NOT_LOCATED; never silently skip an inventory item.

Six-inch support rule (critical correction)
Where two adjacent supports along the same physical pipe route are 6 inches (152.4 mm) apart or less, make the
second/downstream support node BLUE and record the exact measured separation, the two node identities, the dimension
evidence and reason SUPPORT_WITHIN_6_IN. First remains red unless another blue reason applies. If more than 6 inches,
no proximity-based blue flag. Only use engineering dimension chains or verified coordinates; visual sheet distance is not acceptable.
Compare physical support stations, not unrelated branch devices or nearby node bubbles. Persist this status by physical_point_id,
not integer node number.

Historic correction examples: support nodes 30 and 40 at 2 inches must flag second (40) blue; a different close support pair was 0.5
inch, and another was 2 1/8 inches; the previous Node 190 should not be blue solely on six-inch proximity where its support
separation exceeds six inches. During future renumbering, the flag follows the point, not historical labels (such as 40→some new
integer).

Red/blue reasons — typed and auditable
   •       UNVERIFIED_DIMENSION, UNKNOWN_FLANGE_END, UNCONFIRMED_ELBOW_COD,
           UNMATCHED_COMPONENT, PROVISIONAL_CONTINUATION, COORDINATE_MISMATCH,
           UNKNOWN_VALVE_END, UNKNOWN_INSTRUMENT_STATION → BLUE until resolved.
   •       SUPPORT_WITHIN_6_IN → BLUE downstream/second node even if station is fully verified; do not confuse this
           engineering flag with an uncertain location.
   •       No active blue reason, engineering evidence sufficient, no overrides pending → RED (or a separate draft status if project
           rules require).
   •       Store reasons as structured lists, not a single painted RGB value. Any user colour change has to be a reviewed exception
           to the computed rules.

Continuation matching and discrepancies
Search every sheet and drawing for CONT. ON, CONT. FROM, matchline, drawing/sheet references and equipment tie-ins.
Compare complete line ID, size, component identity, topology, E/N/S/EL independent physical coordinates and claimed station. For

match or absent matching sheet, record unresolved endpoint instead of inventing the connection. Also flag smaller mismatches
according to configured engineering tolerance.

6. Deterministic CAESAR node numbering
Precedence: establish physical point identity → group by full line ID → pick engineer-approved main run → number complete main
across all same-line sheets → number each branch away from tee → reproduce identical number on confirmed continuation sheets.
Do not number simply in PDF reading order.
   •      First piping line starts at 10 unless authorised project configuration overrides it. Increment by 10 on main.
   •      Tee intersection belongs to the main pipe and retains its ID when numbering its branch.
   •      After finishing the entire main pipe, start branch 1 at the next higher unallocated multiple of 100 above the main's last
          node, e.g. main ends 330 → first branch 400; branch 2 500, branch 3 600, etc. Reserve non-overlapping ranges; if a
          branch exceeds ten positions, allocate more space rather than collide with another branch.
   •      On the same line across sheet breaks, keep the sequence and repeated continuation ID; sheet break is not line change.
   •      On a new line number, the first new distinct node starts at the next higher 1,000 boundary after the maximum allocated
          ID on the previous line, including its branches, e.g. 1350 → 2000 (not 1360). Returning to a previously registered line
          reuses its established numbering namespace.
   •      A physical shared interface across different lines must not be duplicated: a proved shared point can show its existing node
          ID; subsequent newly distinct nodes on the new line begin at its new thousand.
   •     Save old_node_id → new_node_id, stable physical_point_id, route ordering and all repeated sheet
         instances in an atomic transaction; renumbering must not change any physical station, bubble/leader geometry, red/blue
         reason, or approvals.
def next_higher_multiple(n: int, multiple: int) -> int:
    return ((n // multiple) + 1) * multiple

# Group node candidates by a verified physical_point_id.
# For each first-seen new line in a deterministic processing order:
start = 10 if first_line else next_higher_multiple(previous_line_max_id, 1000)

repeat_confirmed_id_on_all_continuation_instances()

7. Exact dimension engine and physical evidence
   •     Canonical internal numeric model: either millimetres stored as Decimal or exact rational inches, with source unit,
         tolerance and original fraction retained. 6 inches = 152.4 mm; mass kg and weight newtons must never be confused.
   •     Parse mixed feet/inches/fractions, positive/negative Easting and Northing/Southing, elevation, offsets, angular/elbow spec,
         nominal bore and code/rating.
   •     Distinguish source engineering coordinate from PDF view XY and from physical along-centreline station. All are
         explicitly typed (different data models).
   •     Create constraint graph and dimension equations; solve only when sufficiently constrained. Retain exact source text,
         source page and confidence/approval provenance.
   •     For bend COD, infer model intersection from correct engineering dimension convention only; otherwise flag unverified and
         require entered dimensions/CAD/engineer confirmation. Do not extrapolate paper angle or page scale.
   •     For supports, compute along-route distance, not page XY Euclidean distance. Handle branches, elbows and backtracking
         segments correctly.
   •     When constraints disagree, fail validation or request engineer decision; do not silently move the original design data.
   •     Do not infer valve length from symbol width, a default catalogue valve, or another operator style.

8. Flange database module — revised workbook is canonical
Use only PIPE100_Flange_Weights_B16_5_B16_47_API6A_Numbers.xlsx (supersedes the earlier filtered
workbook), imported with a version, hash, rows, units, source URLs, validity status and optional engineering override. Existing tabs:
B16.5, B16.47 Series A, B16.47 Series B, API 6A, Read Me, Constants.
Input key: standard + class/psi rating + true API bore (e.g. pipe NPS 8 is not the API 6A bore 7 1/16) + facing/flange type + any
required end/size constraints. NPS, API bore, class and rating psi are separate columns. Fail on zero or multiple plausible
exact records; do not silently substitute B16.5 for API 6A.

Per flange type on each sheet, print a separate, editable boxed table in unused area, with flange size, class/rating, type, code,
material, stud and nut materials, count and data quality, and at least:
   •     W_flange (N) = flange assembly's reference bare flange weight.
   •     W_half (N) = W_flange + 0.5 × W_all_studs + W_one_nut_per_stud.
   •     W_full (N) = W_flange + W_all_studs + W_two_nuts_per_stud.
Use workbook's published/derived value as the source; don't double-add bolting already included in a manufacturer's assembly
mass. Keep explicit stud_count, length and diameter, nut size, vendor material, source references, calculation/assumption. The
half studs + one nut convention is a project modelling allowance; document its purpose and distinguish from actual installed
assembly deadweight.

1010 regression examples (preliminary, not certified): API 6A 8-inch pipe / 7 1/16-inch bore / 10,000 psi: flange approximately
1,232.5 N, W_half = 1,459.7 N, W_full = 1,686.8 N. API 6A 2-inch pipe / 2 1/16-inch bore / 10,000 psi: flange
approximately 99.1 N, W_half = 117.2 N, W_full = 135.3 N. Sheet 1: 4 × 8-inch flanges; Sheet 2: 6 × 8-inch and 3 × 2-
inch. The workbook uses approximate/estimated geometry in some rows, not supplier-certified hub and full assembly mass. Flag ¼-
inch stud-length discrepancy between ISO and workbook; never silently override.

Catalog changes must version rather than mutate approved historical outputs. Hash the XLSX, validate schema/unit conventions,
derive and snapshot resolved row IDs; display a revision diff. New published database versions do not silently overwrite previous
project PDFs.

Use Valve_Database_Latest.xlsx, not ad hoc values in code. Sheets include ASME B16.10 VALVE DATA BASE,
API 6A Valve Database, audits/sources/coverage/guidance. Explicit fields: valve type, NPS/API bore, code, API WP or class,

Sheet-specific editable boxed valve tables shall show:

13. Security, privacy, tenant isolation and operations
    •     Uploaded PDFs/XLSX/ZIP are untrusted: allowlist type, validate signature, size/pages/zip expansion, virus scan, content
          sandbox/limits; do not execute PDF embedded scripts, macros or arbitrary workbooks; store outside public webroot.
    •     Run PDF parsers in least-privilege isolated workers with CPU/memory/time/size limits, read-only containers where possible
          and no arbitrary network access.
    •     Mandatory authentication, role-based access on every object ID, per-tenant DB row-level enforcement or careful query
          scoping, file encryption at rest, TLS, expiring signed download URLs, admin audit trail, rate limiting and quotas.
    •     Privately store original client drawings; no default public catalogue indexing of project PDFs or telemetry with raw drawings.
          Log identifiers and checksums, not confidential document content.
    •     Maintain backup of PostgreSQL and object storage, periodically perform restoration drills, snapshot every approved
          revision and dataset; retention and deletion policies.
    •     Monitor upload errors, worker crash rates, invalid physical station attempts, missing matches, PDF editability-test failures
          and queue health.
    •     Deploy via Docker to VPS/managed app service with independent queue worker. cPanel may run Python/Node
          applications but basic shared hosting often cannot reliably provide Docker/worker/Redis/storage setup; if cPanel is
          mandatory, first confirm host's permitted services and suitable deployment architecture.

1010 golden fixture (must stay green)
   •     Exactly 2 source sheets with same 8-PG-JE3LN2-1010-FUTURE line → no 1,000-series restart between sheets.
   •     48 unique nodes, 49 displayed node labels, because one logical Node 170 is present on both sheets.
   •     Main node sequence 10–370; three branches 400–430, 500–530, 600–620.

         across both sheets. Preserve component audits rather than hardcode counts for all projects.
   •     Red/blue node assignment follows reviewed physical-point identities and original engineering reasons, including support
         proximity tests. No renumber changes colour or source station.
   •     API 6A 8-inch and 2-inch flange tables contain correct revised-workbook values and material/spec details. Quarter-inch
         stud-length discrepancy remains reported.
   •     Valves: two 8-inch ball-valve reference rows 889 mm / 13,729.31 N with unconfirmed-manufacturer notice; three DBB
         valves remain N/A for unknown length/weight.
   •     Valve warning appears on both sheets. Red X/Y/Z +Mx/My/Mz symbol appears beside NORTH on both without touching it.
   •     Every native object can be enumerated, selected, edited in a test copy and saved/reopened. Baseline 297 annotations in
         v1.2; count may legitimately change if the design evolves, but no silently missing types/elements.
   •     Original PDF content streams unchanged; no annotation obscures existing engineering dimensions, title information or
         materials.

Definition of done for the first usable website
An authorised engineer can upload a new two-sheet PDF, review its materials, manually confirm a main
route/branch/support/endpoints, insert or approve nodes, produce collision-free red/blue and continuation labels, resolve/flag missing
